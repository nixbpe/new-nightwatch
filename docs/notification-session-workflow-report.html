03

Review / repair / binding loop

เลข C คือ candidate binding ไม่ใช่ implementation commit. ทุกครั้งที่แก้ source หลัง bind ต้อง invalidate SHA เดิม, review delta และรัน gates ใหม่ ไม่สามารถนำ green result ของ C ก่อนหน้ามานับแทนได้

จุดตัดสินสำคัญ: รอบ C4 ผ่าน required gates แต่ supplemental AC27 interleaving พบ mark-all สอง transaction; C5 ผ่าน gates แล้วพบ backup code และ cookie รั่วใน logger; C6 ผ่าน gates แล้วเอกสารสถานะถูกแก้หลัง bind ทำให้ต้องสร้าง C7. การซ่อม security Blocker/Major หลัง review budget ต้องเป็น exceptional cycle ที่ user อนุญาตอย่างชัดเจน ไม่ใช่ตัดข้อจำกัดทิ้งหรืออนุมัติทั้งที่ยัง fail

เวลาและ token ที่ใช้จริง

นับจาก timestamp ของ assistant.message.usage ใน session logs ของ Main, Technical Lead, subagents ทุกตัวในสาย delivery และ agents ที่ช่วยเตรียม spec/acceptance; ตัดที่ implementation commit 133be9c เวลา 25 ก.ย. 2026 23:24:47 (UTC+7). ตัวเลขนี้เป็นการใช้ model ของ session นี้ ไม่ใช่จำนวน token ในโค้ด, ชั่วโมงทำงานของคน หรือใบแจ้งหนี้. ไม่รวม advisory process และงานเขียนรายงานหลัง commit

ทำไมช่วง build/integration สูงถึง 432.6M?

นี่คือ time bucket ของ model activity ทุก agent ตั้งแต่ dispatch ถึงเริ่ม review ไม่ใช่ token หรือเวลาของคำสั่ง build. ในช่วง 9 ชม. 37 นาที มี 4,564 model calls: input ใหม่ 8.93M, output 1.12M และ cache reads 422.54M (97.7%) เฉลี่ย 92,582 cached tokens ต่อ call. ยอดใหญ่จึงเป็น context ที่ model ประมวลผลซ้ำ ไม่ใช่ข้อความใหม่ 432.6M tokens หรือ context size ของ call ล่าสุด

Technical Lead ใช้ 197.9M (45.7%); delivery subagents 54 sessions ใช้รวม 223.7M (51.7%); Main และ acceptance agent อีก 11.1M. แปด implementation slices หลักแตกต่อเป็น proof/repair/browser/worker jobs มากกว่าสี่สิบ sessions ระหว่าง phase นี้; การ fan-out กับ context ที่ยาวและถูกอ่านซ้ำเป็นคำอธิบายเชิงปริมาณ ไม่ได้แปลว่า agent เดียวสร้าง 432.6M. ไม่มี responseId ซ้ำใน records ที่มี ID; 6 records ที่ไม่มี ID ใช้ 0 tokens และผลรวม usage แต่ละ record ตรงทุกครั้ง

ผลรวม message.duration ของ calls ในช่วงนี้ราว 10 ชม. 50 นาทีเป็น agent-seconds ที่ซ้อนทับกันได้ ไม่ใช่เวลาที่ผู้ใช้รอหรือเวลาทำงานของคน; 9 ชม. 37 นาทีเป็น elapsed wall-clock ที่รวม tool/DB/browser/wait. ตารางหลักตัด advisor process ออกตามขอบเขตที่ระบุด้านบน; ถ้านับ advisor เพิ่มอีก 41.9M ในช่วงเดียวกัน จะเป็น 474.5M processed tokens แต่ไม่ใช่ยอดในตารางนี้

จุดช้าและงานซ้ำ

  1. Acceptance freeze มาหลัง dispatch request TL หยุดสองครั้งเพื่อรอ PO-authored numbered AC, version และ user/TL approval. งานเริ่มเร็วขึ้นได้โดยจัดเกณฑ์พร้อม spec ก่อนเริ่มแบ่ง slice
  2. Native auth กับ database contract ต้องกลับไปแก้หลายรอบ Better Auth MFA เขียน user flag ก่อน verified row; N0R/N1 ต้องประสาน same-tx writer, legacy projection, re-enrollment และ fault proof ก่อน N3/N4 จะยืนยันเงื่อนไขได้
  3. Shared state ทำให้ false red Auto-migrate draft 0006, shared db:down, global scheduler claim ปะทะ Browser fixture และสอง NightWatch databases ใน cluster เดียวที่เจอ 0008 cluster-global role; สาเหตุเหล่านี้ไม่ใช่ defect ของ feature ทุกครั้ง
  4. Browser test ระบุเวลาหรือ state ผิด Worker dispatch poll ทุก 60 วินาทีแต่ assertion แรกให้ 20 วินาที; เคยลืม reload count query, คาด detail อยู่หลัง reload ทั้งที่ URL ไม่มี item ID, และ fixture preseed ทำ badge ผ่านก่อน origin จริง. แยก fixture/worker และ controlled deferred response จึงพิสูจน์ race ได้
  5. Preflight format/env/scanner มาช้า Lint เริ่มพบ API 103, Web 18, Worker 23, DB 2; Docker frozen install ไม่เห็น workspace ใหม่, Turbo ไม่ pass REDIS_URL, Semgrep default ข้ามไฟล์ tests, baseline Prettier และ async test ขัด root validate. C1–C3 จึงวนที่ gate ไม่ใช่ acceptance behavior
  6. Proof completeness ตรวจหลัง gates Reviewer ขอ privacy/HTTP/cursor/promotion/pagination/mark-all evidence เพิ่มหลัง green suite. AC27 และ AC19 กลายเป็น defect จริง; ต้อง map AC→scenario/artifact ก่อน bind ไม่ใช่คิดว่า suite ผ่านเท่ากับทุก AC ผ่าน

ไม่มี per-task time ledger ที่เชื่อถือได้ รายงานนี้จึงไม่อ้างจำนวนชั่วโมงหรือเปอร์เซ็นต์เวลาที่ประหยัด

07

ทำไม commit เดียว และครั้งหน้าจะแก้ยังไง

ข้อเท็จจริงที่ต้องแยก: ระหว่าง build มีข้อจำกัดที่บันทึกว่า “user authorizes no commits”; subagents จึงไม่ควรสร้าง commit เองจนกว่าผู้ใช้จะสั่ง commit ภายหลัง ผลคือ 133be9c เป็น commit เดียวที่รวม 88 ไฟล์ (+15,940/−168 บรรทัด). การรักษา authorization ถูกต้อง แต่ review, bisect และ revert แย่; ต้องขออนุญาต checkpoint plan ตั้งแต่ต้น ไม่ใช่ให้ agent ฝ่าข้อจำกัด

กติกา commit mode

ให้ TL ระบุ COMMIT_MODE: none | owned-slice หลังถามผู้ใช้ล่วงหน้า. none ห้าม subagent commit แม้ tests ผ่าน; owned-slice ให้ agent ทำใน isolated worktree, stage เฉพาะไฟล์ที่รับผิดชอบ, commit code+regression หลัง focused proof แล้วส่ง SHA ให้ integration owner cherry-pick ตาม dependency. Publish/PR ยังต้องอนุญาตแยก

PR #7 ปัจจุบัน

ไม่ force-push ย้อนหลังเพียงเพื่อให้ history ดู atomic เพราะจะเปลี่ยน SHA ที่ review/gates ผูกไว้. หาก Technical Manager ต้องการประวัติใหม่จริง ให้อนุมัติสร้าง branch ใหม่ แยก dependency-ordered commits ที่ทดสอบได้ทุกก้อน รัน gates/review ใหม่ แล้วจึงตัดสินใจแทน PR
