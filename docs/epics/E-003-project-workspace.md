# E-003 ภาพรวมและการตรวจสถานะบริการภายใต้ Project

| Field          | Value                                                |
| -------------- | ---------------------------------------------------- |
| Direction      | `DIR-001 / v4`, `docs/product-direction.md`          |
| outcome_status | Not measured                                         |
| Owner          | Product Owner role; ยังไม่ยืนยันผู้รับผิดชอบรายบุคคล |

## Outcome

สมาชิก Project เห็นสถานะบริการและเหตุการณ์ของ Project ที่ตนดูแลในที่เดียว และจัดการมอนิเตอร์เฉพาะของ Project นั้น โดยไม่เห็นมอนิเตอร์ของ Project อื่น

## ขอบเขตและกฎสำคัญ

- มอนิเตอร์ทุกตัวสังกัด Project เดียว และ Project สังกัด Organization เดียว
- หน้าภาพรวมและหน้าตรวจสถานะบริการแสดงเฉพาะข้อมูลของ Project ที่เลือก
- ผู้ที่เห็นมอนิเตอร์ได้คือผู้ที่เข้าถึง Project นั้นได้ตาม `E-001` สมาชิก Project อ่านได้ ผู้ดูแล Project และ Owner/Admin องค์กรเขียนได้ การอ่าน header และ body ของ response ปลายทางสงวนให้ผู้ดูแลกลุ่มเดียวกัน
- ตรวจสิทธิ์ Project ก่อน DNS หรือ outbound และตรวจสิทธิ์ปัจจุบันก่อนอ่าน secret ผู้ที่ถูกถอนสิทธิ์ก่อนอ่าน secret ต้องไม่ได้ secret หรือทำให้เกิด outbound
- Project หนึ่งมีมอนิเตอร์ได้ไม่เกิน 20 ตัว และไม่มีเพดานมอนิเตอร์ระดับองค์กร (คำตอบของผู้ใช้ 2026-10-11)
- การแจ้งเตือนของมอนิเตอร์ส่งถึงสมาชิก Project ทุกคนและ Owner/Admin ขององค์กร (คำตอบของผู้ใช้ 2026-10-11) ผู้รับแต่ละคนได้รับครั้งเดียว และต้องตรวจสิทธิ์ปัจจุบันทั้งตอนส่งเข้า inbox และตอนอ่าน ไม่ใช้รายชื่อผู้รับเดิมเป็นสิทธิ์ถาวร
- การสร้างซ้ำด้วยรหัสคำขอเดิมภายใน Project เดียวกันไม่สร้างมอนิเตอร์ซ้ำและไม่ติดเพดานจากต้นฉบับที่นับไปแล้ว รหัสเดียวกันใน Project อื่นเป็นคนละคำขอ
- การสร้างพร้อมกันต้องไม่เกินเพดานของ Project การเขียนมอนิเตอร์กับการลบ Project ต้องประสานกัน และผลตรวจที่มาถึงหลัง Project ถูกลบต้องถูกทิ้ง
- API และ Worker ใช้ลำดับล็อกแถวร่วมกันคือ `monitors` ก่อน `monitor_schedule` ก่อน `monitor_incidents` การล็อก Organization และ Project ใช้ลำดับตาม `E-001` โดย Worker ไม่ล็อก Project
- ภาพรวมแสดงมอนิเตอร์ล่มครบทุกตัวของ Project ตัวเลขสรุปบอกเวลาของข้อมูล และไม่อ้างช่วงเวลาที่ response ไม่ได้ระบุ ค่าที่ยังไม่ทราบไม่แสดงเป็นศูนย์ ข้อมูลเก่าหลังโหลดซ้ำล้มเหลวต้องมีคำเตือน
- การตรวจสถานะบริการยังเป็นความสามารถสนับสนุนตาม `DIR-001` S2
- ไม่ย้ายข้อมูลมอนิเตอร์เดิม ข้อมูลมอนิเตอร์ที่มีอยู่ถูกล้างเมื่อเปลี่ยนเป็นโครงสร้างใหม่ (คำตอบของผู้ใช้ 2026-10-11)

## Features

| Feature | Summary                                                                         |
| ------- | ------------------------------------------------------------------------------- |
| `F-011` | มอนิเตอร์ เหตุการณ์ และการแจ้งเตือนอยู่ภายใต้ Project                           |
| `F-012` | หน้าภาพรวมของ Project                                                           |
| `F-016` | ข้อเสนอภาพรวมรวมทุก Project สำหรับ Owner และ Admin ขององค์กร ต้องออกแบบหน้าก่อน |

ตารางนี้จัดกลุ่มขอบเขต ไม่รายงานสถานะส่งมอบหรืออนุญาตเริ่มงาน ขอบเขตงานใช้คำขอหรือ issue ปัจจุบัน

## Out of scope

- การย้ายมอนิเตอร์ข้าม Project
- การย้ายข้อมูลมอนิเตอร์เดิมเข้า Project

## Risks and dependencies

- `R-01`: การล้างข้อมูลมอนิเตอร์เป็นการลบถาวร ถ้ามี environment ที่มีข้อมูลจริงต้องยืนยันก่อน deploy
- `R-02`: ผู้ชมและผู้ตรวจสอบขององค์กรอ่านมอนิเตอร์ได้เฉพาะ Project ที่เป็นสมาชิก
- `R-03`: หน้าภาพรวมของ Project อยู่ใน `F-012`; ภาพรวมรวมทุก Project เป็นข้อเสนอแยกใน `F-016`
- มอนิเตอร์ใช้ขอบเขตและสิทธิ์ Project ตาม `E-001` การล้างข้อมูลและลำดับ rollout อยู่ใน [runbook](../runbooks/uptime-monitor.md#project-scoped-monitors-f-011)
