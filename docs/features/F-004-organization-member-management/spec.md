## Contracts

### API และ authorization

- ทุก first-party endpoint ใช้ `requireVerifiedSession` (`auth.getSession` ครั้งเดียว), ตรวจ membership จาก `member.organization_id` และ session user id ไม่ใช้ URL, `last_active_tenant_id`, session `active_organization_id` หรือ browser cache เป็นสิทธิ์ UUID ของ Organization ใน URL เป็นเพียง scope hint Validation ตาม shared Zod/OpenAPI; error ของ first-party API ใช้ `{ error: { code, message, details? } }` โดยไม่ echo input หรือ target สำหรับ Organization ที่ไม่มีอยู่และ Organization ที่ actor ไม่เป็นสมาชิก ให้ `403 MEMBERSHIP_DENIED` เหมือนกัน Actor ที่ไม่อนุญาตให้ดูหรือจัดการ target ได้ `403 PERMISSION_DENIED` ก่อน lookup target หลังผ่าน permission แล้ว target ที่ไม่อยู่ใน Organization นี้ให้ `404 MEMBER_NOT_FOUND` เฉพาะเมื่อไม่เปิดเผยข้อมูลที่ actor ไม่มีสิทธิ์ ไม่มี response รายชื่อหรือ PII เมื่อ denied
- เพิ่ม `GET /api/organizations/{organizationId}/members?limit=50&offset=0`: query `limit` เป็น integer `1..50` default `50`; `offset` เป็น integer `>=0` default `0`; `200 { organizationId: uuid, members: [{ id: string, userId: string, name: string, email: string, role: 'owner'|'admin'|'viewer'|'auditor' }], page: { limit: number, offset: number, total: number } }` ใช้ CTE เดียวหา scoped rows, exact `count(*)` และ page rows เพื่อให้ `total` กับ `members` มาจาก statement snapshot เดียว Client มีหน้าถัดไปเมื่อ `offset + members.length < total` และหน้าก่อนเมื่อ `offset > 0` รายชื่อมาจาก Organization เดียว join `member` กับ `user` โดย `organization_id = $1` และ bound parameters ไม่รวม invitation, token หรือ membership ของ Organization อื่น ลำดับคงที่ `lower(user.name), member.id` ไม่รับ sort/filter เฉพาะ `owner`/`admin` อ่านได้ `viewer`/`auditor` ยังเห็นหน้าที่ไม่มีรายชื่อและใช้ self-leave ได้ ใช้ `normalizeOrganizationRole` สำหรับ stored composite roles; unknown role เป็น server error ไม่ลดสิทธิ์แบบเงียบ ประกาศ query/response Zod ใน `packages/api-contract`, route OpenAPI ใน API แล้ว regenerate generated web types
- เพิ่ม `POST /api/organizations/{organizationId}/invitations`: body `{ email: string, role: OrganizationRole }`; trim/lowercase email; response `201 { created: true, emailDispatch: 'accepted'|'failed' }` ไม่ตอบ email, invitation id/token หรือข้อมูลผู้รับ `accepted` หมายถึง configured SMTP transport รับคำขอ ไม่รับรอง delivery `owner` เชิญทุก role; `admin` เชิญได้ `admin`, `viewer`, `auditor`; role อื่นถูกปฏิเสธ ตรวจ role, actor membership, ผู้รับที่เป็น member, pending invitation และ pending count ใน transaction/lock เดียวกับ insert ผู้รับที่เป็นสมาชิกแล้วได้ `409 USER_ALREADY_MEMBER`; pending invitation ที่ยังใช้ได้ได้ `409 INVITATION_ALREADY_PENDING`; pending invitation ทั้ง Organization ครบ 100 ได้ `409 INVITATION_LIMIT_REACHED`; request ไม่มี resend/cancel; concurrent duplicate สร้างได้หนึ่ง row และ loser ได้ `409 INVITATION_ALREADY_PENDING` Invitation ใหม่หมดอายุ 48 ชั่วโมง ใช้ `crypto.randomUUID()` ตาม Better Auth `advanced.database.generateId`, schema และ preview semantics เดิม การเชิญไม่สร้าง member ส่ง SMTP หลัง commitโดยใช้ email builder เดิมและไม่ถือ lock ระหว่าง network call ถ้า SMTP สำเร็จคืน `accepted`; ถ้าล้มเหลวบันทึก sanitized failure แล้วคืน `failed` โดย invitation ยังคงอยู่ ไม่มี automatic retry และการเชิญซ้ำถูกปฏิเสธจน invitation ไม่ pending/หมดอายุ ปิด native `/api/auth/organization/invite-member` ใน middleware guard และ Better Auth hook เมื่อ first-party route พร้อม; คง public preview/signup gate
- เพิ่ม `POST /api/onboarding/invitations/{invitationId}/accept`: ใช้ `requireVerifiedSession`; response `200 { organizationId: uuid }`; pre-read bearer invitation เพื่อหา Organization โดยไม่เปลี่ยน state จากนั้น transaction lock `organization FOR UPDATE`, advisory lock เดิม และ invitation `FOR UPDATE` แล้ว recheck ว่า status `pending`, ยังไม่หมดอายุ และ `lower(invitation.email) = lower(session.user.email)` Unknown, expired, non-pending หรือ recipient mismatch ใช้ `404 INVITATION_NOT_FOUND` เดียวกัน หาก user เป็น member แล้วให้ `409 USER_ALREADY_MEMBER` หาก member count ปัจจุบัน >= 1,000 ให้ `409 ORGANIZATION_MEMBERSHIP_LIMIT_REACHED` และคง invitation เป็น pending ภายใต้ lock เดียวกัน insert `member` ด้วย invitation role/id generation เดิมและ update invitation `pending → accepted`; ทั้งคู่ commit หรือ rollback พร้อมกัน Response ไม่คืน email, role, member id หรือ invitation id Web เปลี่ยนจาก Better Auth client มาใช้ generated first-party client แล้ว invalidate context; selection ไป Organization ใหม่ใช้ `PATCH /api/me/active-org` เดิมหลัง acceptance สำเร็จ หาก selection ถูกปฏิเสธให้แสดง context ล่าสุดที่ server ยืนยัน ปิด native `/api/auth/organization/accept-invitation` ใน middleware guard และ Better Auth hook พร้อม native create; คง public preview และ signup gate
- ใช้ mutation first-party ที่มีอยู่: `PATCH /api/organizations/{organizationId}/members/{memberId}/role` body `{ role: OrganizationRole }`, `DELETE /api/organizations/{organizationId}/members/{memberId}`, `DELETE /api/organizations/{organizationId}/members/me`; ทั้งสามตอบ `200 { member: { id, userId, organizationId, role } }` ประกาศ response ใน shared browser-safe contract และ consume ด้วย generated OpenAPI client พร้อม runtime schema Role update: `owner` จัดการทุก role ตาม last-owner invariant, `admin` จัดการ target ที่ไม่ใช่ ownerไปเป็น non-owner เท่านั้น; revoke: `owner` ถอน owner ได้เมื่อเหลือ owner คนอื่น, `admin` ถอน non-owner; leave: สมาชิกทุก role ออกของตนเอง `400 LAST_OWNER` เมื่อ demote/revoke/leave ทำให้ owner หายไปหมด; validation `400 VALIDATION_ERROR`, unauthenticated `401 UNAUTHENTICATED`, email unverified `403 EMAIL_NOT_VERIFIED`, unexpected `500 INTERNAL_ERROR` ตาม first-party convention UI ไม่แสดง role หรือ removal เป็น success จนได้ response ยืนยันและ refresh list/context ที่เกี่ยวข้อง; denied/failure refresh current server state โดยไม่ replay mutation
- `GET /api/me/context` และ `PATCH /api/me/active-org` เป็น selection contracts เดิม Context คืนเฉพาะ memberships ของ session user และ `lastActiveTenantId` เฉพาะเมื่อยังเป็น member การ revoke/leave ลบ membership แล้วล้าง `user.last_active_tenant_id` กับทุก `session.active_organization_id` ที่ชี้ Organization นั้นใน transaction เดียวกัน Session ยังใช้ได้ แต่ request ถัดไปที่อ้าง Organization เดิมต้องตรวจ membership ใหม่ การสลับ Organization B publish B หลัง server ยืนยัน `PATCH` เท่านั้น; denied ไม่ตั้ง B เป็น active scope

### Data, concurrency, RLS และ audit

- `organization.id` เป็น UUID; `member.id`, `member.user_id` และ `invitation.id` เป็น `text`; unique `(organization_id, user_id)` มีอยู่แล้ว ตั้ง Better Auth organization option `membershipLimit: 1000` เป็น defense in depth แต่ hard cap มาจาก first-party locked acceptance ไม่อาศัย native pre-claim count `organization`, `member`, `user`, `session`, `invitation` เป็น auth/pre-organization tables ที่ไม่มี tenant RLS ตาม DB-06 ดังนั้น scoped membership lookup, join และ permission recheck เป็น authorization boundary ใช้ runtime `nightwatch` non-owner/NOBYPASSRLS และ grants ที่มีอยู่ Tenant-owned tables อื่นยังใช้ existing RLS context ตาม DB-01/DB-04 ไม่มี migration, RLS policy/grant change, table, partition, queue, job, dependency หรือ platform Task ที่ต้องเพิ่ม หาก implementation พบว่าต้องเพิ่ม ให้หยุดและแก้ Spec/ขออนุมัติก่อน
- List และ invite-create precheck actor membership ก่อน Organization lock เพื่อไม่ให้ non-member probe lock Invitation accept pre-read ใช้ bearer id เฉพาะเพื่อ resolve Organization แล้ว recheck invitation ทุก field หลัง lock ภายใน transaction ทุก path ใช้ lock ordering: `organization FOR UPDATE`, advisory transaction lock `notification-membership:${organizationId}`, แล้ว member/invitation rows `FOR UPDATE` ก่อน count/write List recheck actor membership/role ก่อน query; invite-create recheckก่อน insert; accept count กับ insert/updateอยู่ภายใต้ lockเดียวและไม่สร้างสมาชิกคนที่ 1,001 Invites ไม่ส่ง email ใน transaction Role/revoke/leave ใช้ `withLockedOrganization` และ `lockedMember`/`lockedTarget` เดิม Owner count ใช้ exact owner token ตรวจ actor, target และ owner count ภายใต้ lockเดียวก่อน write Mutation ที่แพ้ race ต้องไม่เขียนหรือรายงาน success; transaction rollback เมื่อ error
- Audit denial บันทึก actor user id, fixed action และ code เท่านั้น ไม่บันทึก Organization id, member id, email, name, role, input, invitation id/token หรือ target existence Request completion logging ต้อง normalize affected organization-scoped paths เป็น route templates ก่อน logging รวม 404/validation/failure ตรวจ `app.onError` และ Better Auth logging ว่าไม่ serialize SQL params, PII หรือ secret เปรียบเทียบ Organization/target ที่มีจริงและไม่มีจริงด้วย status, code, message, body และ captured logs/audit ปรับ logging เฉพาะ affected paths ไม่ลด global redaction

### Web, session, cache และ accessibility

- เพิ่ม `/organizations/:organizationId/members` ใต้ `TenantProvider`/`AppShell` และ navigation “องค์กร → สมาชิก” ให้ทุก member role เห็น self-leave; list/row/action จำกัด `owner`/`admin` Header แสดง name และ slug จาก server-confirmed `/api/me/context` Bookmarked URL ที่ไม่ใช่ active scope ต้องตรวจ route Organization membership/permission จาก server ก่อน render และไม่ใช้ activeOrg อื่นแทน route scope Protected loader gate session และ prefetch หน้าแรกด้วย identity query client และ key `['tenant','members', organizationId, { limit: 50, offset }]`; หน้า/offset เป็นส่วนของ cache key และ reset เป็น 0 เมื่อ Organization เปลี่ยนหรือ list invalidated Identity mismatch หยุดก่อน prefetch/render ตาม WEB-04 Browser GET ผ่าน generated OpenAPI paths และ validate response ด้วย shared Zod ตาม WEB-01/WEB-02 ระหว่าง pending ไม่ render rows/cache/action จากหน้าเดิม Failure แสดง “โหลดสมาชิกไม่สำเร็จ” กับ retry และไม่กลายเป็น empty; UI แสดง `total`, previous/next คำนวณจาก `offset`, `members.length` และ `total`, ปิด action ที่ไม่มีหน้าเป้าหมายและมี accessible name
- ใช้ `TENANT_QUERY_PREFIX` cancel/remove old tenant queries เมื่อ switch สำเร็จและเมื่อ denial/context refresh ทำให้ membership เดิมหาย Invalidate member-list pages ทั้ง Organization และ `ME_CONTEXT_QUERY_KEY` หลัง mutation ตามผลจริง Key UI subtree ตาม Organization id และใช้ scope/generation check สำหรับทุก read/mutation completion, notice, confirmation และ form Response ที่ค้างจาก A ไม่เปลี่ยน B เมื่อ switch ไป B สำเร็จ Draft/overlay/page offset ของ A ถูกทิ้ง ถ้า switch ถูกปฏิเสธ A ยัง active หลัง revoke จากอีก session request ที่อ้าง A ถูกปฏิเสธหรือ refreshed context ไม่มี A แล้ว browser ล้าง A scope และนำทางไป active Organization ที่ server ยืนยันหรือ no-access ไม่รับรอง real-time broadcast ข้ามแท็บ ไม่ rollback mutation A ที่ server commit แล้วเพียงเพราะ client switch
- ย้าย invitation UI จาก `WorkspacePage` ไป member page โดยไม่มี duplicate caller `owner` เห็น owner role; `admin` เห็นเฉพาะ non-owner roles Label/error inline, pending ป้องกัน submit ซ้ำ, failure ก่อน insert คง draft เฉพาะ Organization เดิม Success `emailDispatch='accepted'` แสดง “สร้างคำเชิญแล้ว”; `failed` แสดง “สร้างคำเชิญแล้ว แต่อีเมลส่งไม่สำเร็จ” เป็น warning และไม่ retry อัตโนมัติ ทั้งสองกรณีไม่เพิ่ม invitee เป็น member Role change ที่เกี่ยวกับ owner และ revoke/self-leave ใช้ dialog ยืนยัน target/actor, Organization และผลกระทบ Non-owner role change ไม่ต้อง confirmation Cancel/close ไม่ส่ง mutation; pending ป้องกันส่งซ้ำ; `LAST_OWNER` อธิบาย invariant และ refresh state ที่ server ยืนยัน
- Table ใช้ header name/email/role และ keyboard actions Overlay มี accessible name, close/cancel, focus trap, Escape, return to opener เมื่อยังอยู่ หรือ heading/action ที่อยู่จริงเมื่อ row ถูกลบหรือ switch scope Status/error เป็น live announcement และ field labels/error associations ถาวร Visible focus และ non-color cues ตาม `docs/design-system.md` COL-03, LAY-02/03, CMP-01/02/03, A11Y-01 ทดสอบ light/dark, narrow และ text zoom 200% ใช้ pattern ที่มีอยู่หรือ native dialog ที่พิสูจน์ focus ได้ ไม่เพิ่ม dependency dialog จากหลักฐานปัจจุบัน

### Jobs

ไม่มี background job, queue payload, retry policy หรือ idempotency work itemใหม่ ใช้ SMTP/acceptance เดิม Invitation success แยก SMTP transport accepted กับ failed โดยไม่รับรอง delivery SMTP failure หลัง commit คืนคำเตือน ไม่ลบ invitation และไม่สร้าง automatic retry

## Design decisions

- Isolation/security/privacy: list contract enforce permission ใน API และไม่คืน PII บน denied/failure Web guard มีหน้าที่ UX เท่านั้น ไม่เพิ่ม RLS บน pre-organization auth tables เพราะต้อง lookup membership ก่อน tenant context
- Concurrency/invariant: serialize affected membership reads/writes/invite create/accept ด้วย lock order ที่มีอยู่ ตรวจ actor/target/owner count/member cap ใน critical section Legacy invite create และ accept routes ปิดเมื่อ first-party replacements พร้อม เพราะ create เป็นทางเลี่ยง AC-05 และ native accept ตรวจ cap ก่อน claim โดยไม่มี Organization lock Public preview/signup gate คงไว้
- Maintainability/review: หนึ่ง PR ต่อ Story behavior Route/page/contract/proof อยู่ด้วยกัน Foundation ที่ต้องแชร์สำหรับ directory อยู่ใน `NODE-F004-01`; AC-16/AC-17 อยู่กับทุก slice ที่แตะและตรวจรวมตอนจบ ไม่ทำ horizontal foundation PR หรือ correctness-only PR

### Parallel and shared-file policy

- Node 01 establishes member-list contracts, tenant query keys, member-page composition and loader behavior. No later node starts before its merge and accepted handoff.
- Nodes 02 and 03 have no behavioral dependency on each other, so source implementation may run in parallel in separate branches/worktrees after node 01. They keep invitation and role behavior in separate modules/components.
- Nodes 02 and 03 still touch shared composition and may regenerate the same OpenAPI file. Merge is serialized: node 02 first; node 03 rebases, resolves the single integration delta, reruns focused verification and then enters final review. No sibling edits the same shared file in the same worktree.
- Node 04 depends on node 03's shared confirmation/dialog contract. Node 05 depends on node 04's revocation/context transition. Implementing either complete PR early would create duplicate UI or tenant-transition conventions, so both remain serial.
- The current node owner owns shared files only until handoff. Each PR contains one vertical behavior and its API/UI/proof. Focused checks run per PR. Full gates run once after all writers stop.
