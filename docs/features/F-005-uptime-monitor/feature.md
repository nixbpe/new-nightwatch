## Problem and scope

ผู้มีปัญหา (สมมติฐาน ไม่มีหลักฐาน discovery): ทีม Platform/SRE ของ provider (D1, D6) ต้องรู้ว่า endpoint HTTP(S) และ REST API ที่ Organization หนึ่งระบุ ล่ม ตอบช้า หรือใบรับรอง SSL ใกล้หมดอายุ พร้อมเหตุผลที่ตรวจสอบได้ ไม่พบงานวิจัย interview หรือคำขอจากลูกค้า ที่มาเดียวคือคำขอของผู้ใช้ Uptime Monitor ไม่ใช่งานหลักตาม positioning ของ DIR-001

- In scope (MVP, `F-005-S01` ถึง `F-005-S08`):
  - Basic: monitor HTTP/HTTPS, UP/DOWN, response time, expected HTTP status, uptime %, SSL expiry และ warning
  - Advanced: method, headers, query params, request body, expected status code, assertions สามชนิด (JSONPath เท่ากับค่า, body มีข้อความ, response time ต่ำกว่า threshold) พร้อมผ่าน/ไม่ผ่านต่อ assertion
  - Advanced auth (Bearer token, Basic, API key header) และ header ที่ติดป้ายลับ ภายใต้ S3 exception แบบจำกัด
  - Test Configuration ผ่าน server
  - Overview, Detail, Create, Edit, Pause/Resume, Delete
  - แจ้งเตือนล่ม กลับมาปกติ และ SSL เข้าเกณฑ์ ผ่าน in-app notification ที่มีอยู่
  - Organization scope และ top-level nav leaf "ตรวจสถานะบริการ" icon `activity`
- Non-goals:
  - ช่องแจ้งเตือนอื่นนอก in-app (email, Slack, webhook)
  - status page สาธารณะ
  - ตรวจจากหลาย region
  - Project scope
  - maintenance window
  - โปรโตคอลอื่นนอก HTTP(S) (TCP, ICMP, DNS)
  - assign หรือ ticket ของ incident (D5)
  - เก็บ response body เต็ม
  - SLO และ error budget
  - credential ลูกค้าประเภทอื่นนอก auth และ header ลับของ monitor (ยังอยู่ใต้ S3)

Organization เป็น tenant boundary ทุก operation ตรวจ session, membership และ permission ที่ server ค่า Organization จาก URL ไม่ให้สิทธิ์ ข้อมูล monitor ของ Organization A ต้องไม่ปรากฏใน Organization B

### Health model

health, freshness และ SSL แยกกันตาม Evidence surfaces ใน `docs/design-system.md`

| แกน | ค่า | Tone ของ `StatusPill` (COL-01: สีที่ตัวอักษรหรือ icon) |
| --- | --- | --- |
| Health | ปกติ (UP) | `primary` + CheckIcon |
| Health | ล่ม (DOWN) | `danger` |
| Health | ไม่ทราบสถานะ (UNKNOWN: ยังไม่เคยตรวจ หรือผลล่าสุดเก่ากว่า 2 เท่าของรอบตรวจ) | `neutral` พร้อมเหตุผลเป็นข้อความ |
| Health | หยุดชั่วคราว (PAUSED) | `muted` |
| Freshness | "ตรวจล่าสุด 14:30" / "รอตรวจครั้งแรก" / "ไม่มีผลใหม่ตั้งแต่ 13:10" | ข้อความ ไม่ใช่ pill |
| SSL | ปกติ / ใกล้หมดอายุ (เหลือไม่เกิน 30 วัน) / วิกฤต (เหลือไม่เกิน 7 วัน) / หมดอายุแล้ว / ไม่ใช้ HTTPS / อ่านใบรับรองไม่ได้ / ยังไม่มีข้อมูล | neutral / caution / danger / danger / muted / neutral / neutral |

กฎ:

- ผลเก่ากว่าเกณฑ์ความสดทำให้ health เป็น "ไม่ทราบสถานะ" ถ้าผลล่าสุดที่ทราบคือล่ม แสดง "ล่าสุดทราบว่าล่ม" และ incident ยังเปิดอยู่
- ล้มเหลวครั้งเดียวไม่เปลี่ยน health แสดงข้อความ caution "ล้มเหลว 1 ครั้ง" ข้าง pill
- Assertion ไม่ผ่านนับเป็นการตรวจที่ล้มเหลว MVP ไม่มี DEGRADED
- Uptime % นับเฉพาะการตรวจที่มีผล ไม่รวมช่วงหยุดชั่วคราวและช่วงไม่ทราบ แสดง coverage ("คำนวณจากการตรวจ 288 ครั้ง ข้อมูลครอบคลุม 98% ของช่วง") ไม่นับช่วงไม่มีข้อมูลเป็น UP
- SSL เป็นแกนเตือนแยก ไม่เปลี่ยน health แต่ใบรับรองที่ตรวจสอบไม่ผ่าน (หมดอายุ, ชื่อไม่ตรง, chain ไม่น่าเชื่อถือ, self-signed) ทำให้การตรวจล้มเหลว (AC-35)
- ความล้มเหลวฝั่ง NightWatch บันทึกเป็น "ตรวจไม่ได้" ไม่นับเป็นล้มเหลวของเป้าหมาย ไม่เปิด incident และไม่นับใน uptime % (AC-39)
- Assertion ที่ไม่มี response ให้ประเมิน (DNS, TLS, timeout, ถูกบล็อก, redirect เกิน) แสดง "ไม่ได้ประเมิน" ไม่ใช่ "ผ่าน" หรือ "ไม่ผ่าน" (AC-32)
- หลังบันทึกการแก้ที่เปลี่ยนคำขอหรือเงื่อนไขตรวจ health เป็น "ไม่ทราบสถานะ" จนมีผลตรวจของค่าใหม่ (AC-40)

### C1 สร้าง (`owner`, `admin`)

1. ผู้ใช้เปิด "ตรวจสถานะบริการ" จาก sidebar หรือ ⌘K หน้าแสดง Overview
2. ผู้ใช้กด "เพิ่มมอนิเตอร์" หน้าไป `/monitors/new` โฟกัสที่ h1 โหมดเริ่มต้น "พื้นฐาน"
3. ผู้ใช้กรอกชื่อ, URL, รอบการตรวจ (1, 5 หรือ 15 นาที ค่าเริ่มต้น 5) ถ้าต้องการกำหนดคำขอหรือการยืนยันตัวตน สลับเป็น "ขั้นสูง" ค่าที่กรอกไม่หาย
4. ผู้ใช้กด "ทดสอบการตั้งค่า" (ไม่บังคับ) server ส่งคำขอจริงหนึ่งครั้ง ผลขึ้นในกล่องผล (`role="status"`) โฟกัสอยู่ที่ปุ่มเดิม ไม่บันทึก monitor ถ้าแก้ฟอร์มหลังทดสอบ ผลเดิมติดป้าย "ผลนี้ไม่ตรงกับค่าปัจจุบัน"
5. ผู้ใช้กด "บันทึกมอนิเตอร์" ปุ่มแสดง pending และกันกดซ้ำ ถ้า server ปฏิเสธ error อยู่ข้างช่อง ค่าคงอยู่ โฟกัสไปช่องแรกที่ผิด
6. บันทึกสำเร็จ หน้าไป Detail สถานะ "ไม่ทราบสถานะ" พร้อม "รอตรวจครั้งแรก" และ Notice "สร้างมอนิเตอร์แล้ว"
7. ระบบตรวจครั้งแรกในรอบ poll ถัดไป (ประมาณ 10 วินาทีหลังบันทึก) ผลแรกมา สถานะเป็น "ปกติ" หรือยังเป็น "ไม่ทราบสถานะ" พร้อม "ล้มเหลว 1 ครั้ง" (ยังไม่ล่มจนล้มเหลวติดกัน 2 ครั้ง) ประกาศครั้งเดียว

### C2 แก้ไข (`owner`, `admin`)

1. ผู้ใช้กด "แก้ไข" ใน Detail หน้าไป `/edit` ฟอร์มมีค่าเดิม เปิดโหมดขั้นสูงเองถ้ามีค่าขั้นสูง
2. ค่าลับแสดง "ตั้งค่าแล้ว" และปุ่ม "แทนที่" ค่าเดิมไม่แสดงอีก ถ้าไม่กดแทนที่ ระบบใช้ค่าเดิมต่อ
3. ผู้ใช้กด "บันทึกการแก้ไข" สำเร็จแล้วกลับ Detail พร้อม Notice "บันทึกการแก้ไขแล้ว"
4. ถ้า version ชนกัน หน้าแสดง "มอนิเตอร์นี้ถูกแก้โดยผู้อื่น โหลดใหม่เพื่อดูค่าล่าสุด" ค่าที่กรอกยังอยู่

### C3 หยุดชั่วคราวและเริ่มต่อ (`owner`, `admin`)

1. ผู้ใช้กด "หยุดชั่วคราว" ไม่มี dialog ปุ่มเดิมเปลี่ยน label เป็น "เริ่มต่อ" โฟกัสไม่หลุด สถานะเป็น "หยุดชั่วคราว"
2. ผู้ใช้กด "เริ่มต่อ" สถานะเป็น "ไม่ทราบสถานะ" จนมีผลใหม่ ห้ามแสดง "ปกติ" จากผลเก่า

### C4 ลบ (`owner`, `admin`)

1. ผู้ใช้กด "ลบมอนิเตอร์" dialog ยืนยันเปิด โฟกัสเริ่มที่ "ยกเลิก"
2. ผู้ใช้ยืนยัน หน้าไป Overview พร้อม Notice และโฟกัส h1
3. ถ้าลบไม่สำเร็จ dialog ปิด โฟกัสกลับปุ่มเปิด และมี Alert error

### C5 `viewer` และ `auditor`

1. ผู้ใช้เห็น leaf, Overview และ Detail ไม่เห็นปุ่มเพิ่ม, แก้ไข, หยุด, เริ่มต่อ, ลบ, ทดสอบ status line แสดง "สิทธิ์ของคุณ: ดูอย่างเดียว"
2. ผู้ใช้เปิด `/new` หรือ `/edit` ตรง หน้าแสดง denied state

### C6 แจ้งเตือน

1. monitor ล่ม กลับมาปกติ หรือ SSL เข้าเกณฑ์ ระบบสร้างรายการใน `/notifications` ของ `owner` และ `admin` พร้อมลิงก์ "เปิดมอนิเตอร์"

### Accessibility

- ทุกหน้า: หลังสร้าง บันทึก หรือลบ ย้ายโฟกัสไป h1 (`tabIndex={-1}` แบบหน้า members) สถานะเป็นคำเสมอ ไม่พึ่งสี "ไม่มีข้อมูล" เป็นข้อความที่อ่านได้ เวลาใช้ `<time dateTime>` และระบุ timezone ในหัวคอลัมน์และแกนกราฟ
- Overview: ลำดับ Tab คือ เพิ่มมอนิเตอร์, รีเฟรช, ค้นหา, ตัวกรอง, ตาราง, ลิงก์ในแถว, pagination ผลกรองประกาศ "พบ 3 จาก 12" ผ่าน `role="status"` ไม่ประกาศทุก auto refetch summary tile เป็นข้อความ ไม่ใช่ปุ่ม
- Create/Edit: label ถาวร error ผูก `aria-describedby` โฟกัสช่องแรกที่ผิด `SegmentedControl` ของโหมดและรอบตรวจเป็น radiogroup มี label แถวที่เพิ่มลบได้มีชื่อเฉพาะแถว ("ลบ header แถวที่ 2") หลังเพิ่มโฟกัสช่องแรกของแถวใหม่ หลังลบโฟกัสแถวถัดไปหรือปุ่มเพิ่ม ช่องค่าลับใช้ `type="password"` และไม่ autocomplete
- Test: พื้นที่ผลเป็น `role="status"` (polite) อยู่ใน DOM ตั้งแต่แรก ประกาศสรุปสั้น โฟกัสค้างที่ปุ่ม ช่วง rate-limit ไม่ประกาศนับถอยหลังทุกวินาที
- Detail: section เป็น `h2` กราฟมีสรุปข้อความ (หน่วย, ช่วงเวลา, แหล่ง, ช่วงไม่มีข้อมูล) และตารางทางเลือกเป็น `<table>` จริง (CMP-05) ปุ่ม Pause สลับ label โดยไม่ unmount
- Dialog: ตาม `MemberActionDialog` (`role="dialog"`, `aria-modal`, โฟกัสเริ่ม "ยกเลิก", Tab วนใน dialog, Escape ปิดเมื่อไม่ pending, คืนโฟกัสปุ่มเปิดหรือ h1)
- ตรวจหลัง implement: สองธีม, keyboard ทุก flow, screen reader, contrast ของ pill zoom และ reflow ตาม LAY-02 ตรวจเมื่อผู้ใช้ขอ
