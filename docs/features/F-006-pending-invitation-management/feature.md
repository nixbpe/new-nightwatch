## Problem and scope

คำขอของผู้ใช้ (verbatim):

- ในหน้าการจัดการ member อยากเห็นรายการ email ที่ส่ง invite ไปแล้ว และยังไม่ accept ด้วย
- ในหน้าการจัดการ member ต้องการสามารถจัดการ email ที่ส่ง invite ไปแล้วได้ด้วย

ผู้ดูแล Organization สร้างคำเชิญได้แล้วใน `F-004` แต่มองไม่เห็นว่าคำเชิญใดยังรอตอบรับ เขาจึงไม่รู้ว่าทำไมเชิญอีเมลหนึ่งซ้ำไม่ได้ (`INVITATION_ALREADY_PENDING`) หรือทำไม Organization ชนเพดาน 100 คำเชิญที่รอตอบรับ (pending invitation) เขายังส่งอีเมลใหม่หรือเพิกถอนคำเชิญที่ส่งผิดไม่ได้

คำว่า "จัดการ" ในคำขอตีความเป็นสามอย่าง: ดูรายการ, ส่งซ้ำ และยกเลิก (`A-01`)

คำเชิญ `owner` ที่ operator สร้างด้วย `bun run provision:organization` อยู่ในรายการเดียวกัน Technical Lead พบใน Technical Spec (หัวข้อ Risks) ว่า provisioning ของ Organization ที่มีอยู่แล้ว 1) insert คำเชิญ `owner` โดยไม่ตรวจโควตา 100 2) ตรวจคำเชิญซ้ำของอีเมลโดยไม่ lock Organization จึงเกิดคำเชิญที่ยังไม่หมดอายุสองแถวต่ออีเมลได้ 3) re-send โดยไม่ออกลิงก์ใหม่ ไม่อัปเดตวันที่ส่ง และอาจส่งลิงก์ที่ resend ของ `F-006` ทำให้ใช้ไม่ได้แล้ว ผู้ใช้เลือกรวม provisioning ใน `F-006` (`OD-13`) เพื่อให้กฎโควตาและกฎ resend ใช้กับทุกทางที่สร้างหรือส่งคำเชิญ

- In scope:
  - ดูรายการคำเชิญที่ยังไม่ตอบรับของ Organization ที่เลือก บนหน้า "องค์กร → สมาชิก" เดิม รายการรวมคำเชิญที่หมดอายุพร้อมป้าย "หมดอายุ"
  - ส่งคำเชิญซ้ำ (resend) หลังผู้ใช้ยืนยัน: ผู้รับได้ลิงก์ใหม่อายุ 48 ชั่วโมงนับจากเวลา resend ลิงก์เดิมใช้ไม่ได้ แต่ละคำเชิญมี cooldown (ช่วงรอก่อนส่งซ้ำได้อีก)
  - ยกเลิกคำเชิญ (cancel) หลังผู้ใช้ยืนยัน
  - แยก state loading, empty, denied, failure และ success ทุก state ไม่ใช้ข้อมูลจาก Organization เดิม
  - Operator provisioning (`bun run provision:organization`) ของ Organization ที่มีอยู่แล้ว: เคารพโควตา 100 คำเชิญที่ยังไม่หมดอายุ, ไม่สร้างคำเชิญที่ยังไม่หมดอายุแถวที่สองของอีเมลเดียวกัน และ re-send ส่งลิงก์ที่ใช้ได้ตามกฎ resend ของ `F-006` (ลิงก์ใหม่ อายุ 48 ชั่วโมง ลิงก์เดิมใช้ไม่ได้) Provisioning เป็น CLI ไม่มี UI ผลที่ตรวจได้คือ output และ exit code ของคำสั่ง, สถานะคำเชิญ และรายการคำเชิญบนหน้า "องค์กร → สมาชิก"
- Non-goals:
  - เปลี่ยน role ของคำเชิญ: ผู้ใช้ต้องยกเลิกแล้วเชิญใหม่
  - แสดงชื่อผู้เชิญ
  - Bulk resend หรือ bulk cancel
  - ประวัติคำเชิญที่ตอบรับหรือยกเลิกแล้ว และ audit report UI
  - Delivery tracking (เปิดอ่าน, bounce) หรือรับประกันว่าอีเมลถึงผู้รับ
  - แก้ไขอีเมลผู้รับของคำเชิญเดิม
  - เปลี่ยน flow การตอบรับคำเชิญ, การเชิญใหม่ หรือ member cap 1,000 ของ `F-004`
  - กำหนด release หรือ outcome metric
  - UI สำหรับ provisioning และการเปลี่ยน argument, พฤติกรรมการสร้าง Organization ใหม่ หรือ internal provisioning principal ของคำสั่ง

Organization เป็น tenant boundary (ขอบเขตข้อมูลที่แยกแต่ละองค์กรออกจากกัน) server ต้องตรวจ session, membership และ permission ของทุก operation ค่า Organization จาก URL, browser หรือ session mirror ไม่ให้สิทธิ์ คำเชิญของ Organization A ต้องไม่ปรากฏใน Organization B

### Permission matrix

| Operation | owner | admin | viewer / auditor | non-member |
| --------- | ----- | ----- | ---------------- | ---------- |
| ดูรายการคำเชิญที่ยังไม่ตอบรับ (รวมแถว role `owner`) | อนุญาต | อนุญาต | ไม่อนุญาต | ไม่อนุญาต |
| ส่งซ้ำหรือยกเลิกคำเชิญ role `owner` | อนุญาต | ไม่อนุญาต (เห็นแถว ไม่มีปุ่ม) | ไม่อนุญาต | ไม่อนุญาต |
| ส่งซ้ำหรือยกเลิกคำเชิญ role `admin`, `viewer`, `auditor` | อนุญาต | อนุญาต | ไม่อนุญาต | ไม่อนุญาต |

### กฎโควตา 100 pending invitation

- นับเฉพาะคำเชิญ pending ที่ยังไม่หมดอายุ คำเชิญที่หมดอายุแสดงในรายการแต่ไม่นับในโควตา
- Cancel คืนโควตาทันที
- Resend คำเชิญที่ยังไม่หมดอายุไม่เพิ่มจำนวน
- Resend คำเชิญที่หมดอายุทำให้คำเชิญกลับมานับในโควตา ถ้าคำเชิญที่ยังไม่หมดอายุครบ 100 แล้ว server ปฏิเสธด้วย `INVITATION_LIMIT_REACHED` และไม่เปลี่ยนคำเชิญ
- Operator provisioning ใช้กฎเดียวกัน: การสร้างคำเชิญ `owner` ใหม่ใน Organization ที่มีคำเชิญที่ยังไม่หมดอายุครบ 100 ถูกปฏิเสธ re-send คำเชิญ `owner` ที่ยังไม่หมดอายุไม่เพิ่มจำนวน (`AC-16`, `AC-18`)

## UI flow

Product Owner เขียน UI flow นี้ร่วมกับ UX Designer ยังไม่ผ่าน visual, keyboard หรือ screen-reader verification Confirmation (กล่องยืนยันก่อนทำรายการ) ของ resend ใช้ pattern เดียวกับของ cancel

1. `owner` หรือ `admin` เปิด "องค์กร → สมาชิก" Server ตรวจ session, membership และ permission ก่อน แล้วโหลดเฉพาะคำเชิญของ Organization ที่เลือก ระหว่างตรวจ หน้าไม่แสดงข้อมูลจาก cache ของ Organization ก่อนหน้า
2. Section "คำเชิญที่รอตอบรับ" อยู่ต่อจากการ์ดเชิญสมาชิกและก่อนตารางสมาชิก
   - หัวข้อแสดง "n จาก 100" (n คือจำนวนคำเชิญที่ยังไม่หมดอายุ) พร้อมข้อความ "คำเชิญที่หมดอายุไม่นับในโควตา"
   - ตารางมีคอลัมน์ อีเมล, บทบาท, วันที่ส่ง, วันหมดอายุ และการทำงาน คำเชิญที่หมดอายุมีป้ายข้อความ "หมดอายุ" ในคอลัมน์วันหมดอายุ
   - คำเชิญแยกจากตารางสมาชิก เพราะผู้รับยังไม่เป็นสมาชิก
   - `viewer` และ `auditor` ไม่เห็น section นี้ และไม่มีข้อความใบ้ว่ามี
   - รายการเรียงจากวันที่ส่งล่าสุดก่อน หน้าละไม่เกิน 50 แถว ใต้ตารางมีจำนวนคำเชิญทั้งหมดในรายการ (รวมที่หมดอายุ) และปุ่ม "หน้าก่อนหน้า"/"หน้าถัดไป" แบบตารางสมาชิก ตัวนับ "n จาก 100" ไม่ขึ้นกับหน้าที่เปิด
   - เมื่อเปลี่ยนหน้า section แสดง loading โดยไม่แสดงแถวของหน้าเดิม เมื่อโหลดเสร็จ focus ไปที่ heading ของ section
3. `admin` เห็นแถวคำเชิญ role `owner` แต่ไม่มีปุ่ม แถวนั้นมีข้อความ "เฉพาะเจ้าของจัดการได้"
4. หลังสร้างคำเชิญจากการ์ดเชิญสำเร็จ (ทั้งเมื่อ SMTP รับและไม่รับอีเมล) รายการ refresh และคำเชิญใหม่อยู่ต้นหน้าแรก ถ้าอีเมลนั้นมีคำเชิญที่หมดอายุอยู่ create ของ `F-004` เปลี่ยนแถวที่หมดอายุเป็นยกเลิก รายการจึงเหลือแถวเดียวของอีเมลนั้น (create ไม่ล้างแถวซ้ำที่มีอยู่ก่อน migration)
5. ผู้มีสิทธิ์กด "ส่งซ้ำ" แล้ว confirmation เปิดขึ้น ระบุอีเมลผู้รับ, role ที่เชิญ, ชื่อ Organization และผลกระทบ "ลิงก์เชิญเดิมจะใช้ไม่ได้ ระบบส่งลิงก์ใหม่ที่มีอายุ 48 ชั่วโมง" ปุ่ม "กลับ" หรือ Escape ไม่ส่ง request
6. หลังยืนยัน confirmation แสดง "กำลังส่ง…" และกันการกดส่งซ้ำ
   - สำเร็จ: แสดง "ส่งคำเชิญซ้ำแล้ว"
   - SMTP ไม่รับอีเมล: แสดงคำเตือน "ส่งคำเชิญซ้ำแล้ว แต่อีเมลส่งไม่สำเร็จ" และไม่ส่งซ้ำอัตโนมัติ
   - ทั้งสองกรณี วันที่ส่งใหม่ทำให้คำเชิญขึ้นต้นรายการ UI จึงโหลดหน้าแรกหลัง server ยืนยัน resend และแสดงวันที่ส่งกับวันหมดอายุตามที่ server ยืนยัน
   - Cooldown คือ 300 วินาทีนับจากเวลาส่งล่าสุด (สร้างหรือ resend) และนับแม้ SMTP ล้มเหลว ระหว่าง cooldown ปุ่ม "ส่งซ้ำ" ของแถวนั้นยังอยู่แต่กดไม่ได้ พร้อมข้อความ "ส่งซ้ำได้อีกครั้งเมื่อ {เวลา}"
7. ผู้มีสิทธิ์กด "ยกเลิกคำเชิญ" แล้ว confirmation เปิดขึ้น ระบุอีเมลผู้รับ, role ที่เชิญ, ชื่อ Organization และผลกระทบ "ลิงก์เชิญเดิมจะใช้ไม่ได้ ผู้รับต้องได้รับคำเชิญใหม่จึงจะเข้าร่วมได้" ปุ่ม "กลับ" หรือ Escape ไม่ส่ง request
8. หลังยืนยัน cancel UI กัน action อื่นใน section จนได้ผล แล้ว refresh รายการ
   - Success แสดงเฉพาะเมื่อ server ยืนยันการยกเลิก และรายการล่าสุดไม่มีคำเชิญนั้น
   - อีเมลนั้นเชิญใหม่ได้จากการ์ดเชิญ
   - UI คงหน้าเดิม แถวจากหน้าถัดไปเลื่อนขึ้นมาแทน ถ้าหน้าเดิมไม่เหลือแถวและไม่ใช่หน้าแรก UI โหลดหน้าสุดท้ายที่มีแถว
9. ถ้า refresh ใดพบว่าหน้าที่เปิดอยู่เกินจำนวนหน้าที่มีจริง (เช่น อีก session ยกเลิกคำเชิญ) UI โหลดหน้าสุดท้ายที่มีแถว ถ้าไม่เหลือคำเชิญเลย UI แสดง empty
10. ถ้าอีก session ตอบรับ ยกเลิก หรือเปลี่ยนสถานะคำเชิญก่อน server ตัดสิน หรือ permission ของผู้ใช้เปลี่ยน UI แสดง error หรือ denied แล้ว refresh เป็นค่าล่าสุด UI ไม่ส่ง request เดิมซ้ำ (replay) และไม่แสดง success ถ้า server ปฏิเสธเพราะ role หรือ membership ของผู้ใช้เปลี่ยน UI โหลดข้อมูลสมาชิกภาพและ role ของผู้ใช้ใหม่ (membership context) ตาม pattern ของ `F-004`
11. เมื่อสลับ Organization UI ล้างรายการ, confirmation, notice และผลของ request ที่ค้างจาก Organization เดิม แล้วเริ่มที่หน้าแรก ตาม pattern ของ `F-004` `AC-16`

| Screen | Loading / pending | Empty | Error และ recovery | Denied | Success |
